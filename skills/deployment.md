# Deployment and Operations Skill

- The default production deployment uses root `docker-stack.yml` for Spoolman, Filament Manager web, and the worker. It assumes remote PostgreSQL and creates its overlay network and application data volumes.
- The independent `docker/spoolman-stack.yml` and `docker/filament-manager-stack.yml` files remain supported when separate application lifecycle boundaries are required.
- In either deployment, use distinct PostgreSQL databases, roles, credentials, migrations, and backups. A combined application stack never authorizes cross-database access.
- Remote PostgreSQL uses the `filament_user` and `spoolman_user` roles with explicit non-SSL client settings on the operator-managed isolated database network. Keep SCRAM authentication and restrict database routing, firewall rules, and `pg_hba.conf` entries to approved Swarm nodes.
- Docker deployments do not mount an application configuration file. All deployer-supplied addresses, one-printer Moonraker settings, integration settings, operational tuning, and credentials come from stack environment variables; fixed invariants remain application defaults.
- Docker credentials currently use ordinary stack environment variables rather than Docker secrets. Keep populated `.env` files untracked and `0600`, restrict Swarm-manager and Portainer access, and document that service specifications expose environment values to authorized operators.
- Filament Manager services receive only the canonical database URL, Google credential, and Moonraker API key variables. Account credentials are not deployment variables: startup creates the exact first-install `admin` / `admin` account only when the database is empty and forces its password change. Filament Manager must not receive the Spoolman database password or PostgreSQL administrator credential.
- Moonraker uses the stable LAN Spoolman endpoint, never Swarm-only DNS.
- The current Docker variable contract supports one Moonraker printer. `MOONRAKER_WEBSOCKET_URL` may be empty so the application derives `/websocket` from `MOONRAKER_BASE_URL`.
- Pin tested image tags or digests. Spoolman uses one replica and stop-first updates. Filament Manager uses one replica until session and worker concurrency have been validated for scale-out.
- After CI passes for `main`, `publish-swarm-image.yml` publishes AMD64 and ARM64 Filament Manager images with `latest` plus an immutable `sha-<commit>` tag. Use `latest` only for testing and pin the SHA tag or digest for production. Package publication remains separate from Git tagging and GitHub Releases.
- Web and worker container commands automatically run Alembic before application startup. Concurrent Swarm tasks serialize with a PostgreSQL advisory lock and stop on migration failure. Retain a separate `alembic upgrade head` job only as an optional diagnostic or recovery tool, and set `FILAMENT_MANAGER_DATABASE_AUTO_MIGRATE=false` only during an intentional maintenance procedure.
- The image health check belongs only to the web process. It probes loopback with the hostname from `FILAMENT_MANAGER_BASE_URL` so `TrustedHostMiddleware` still validates the request. Explicitly disable the inherited health check on worker, migration, seed, or other non-HTTP commands.
- Local Compose passes separate database-role variables only to PostgreSQL initialization and the service that owns each role. Never reuse the PostgreSQL administrator password for an application role.
- Back up `filament_manager` and `spoolman` independently and perform isolated restore tests.
- Use Diagnostics or `filament-manager-cli verify` for read-only migration, measurement, credential, projection, and deployment validation. Use `filament-manager-cli rebuild-projections --confirm` only to requeue derived Spoolman, Google, and managed Cura state; it is not a database restore.
- Verify `/health/live`, `/health/ready`, `/metrics`, Diagnostics connection/worker status, outbox depth, reconciliation lag, and publication lag after deployment.
- Inventory mutations normally reach Spoolman through the immediate outbox within one worker polling cycle. Keep `SPOOLMAN_RECONCILE_INTERVAL_MINUTES=1` as the complete convergence safety net, `MOONRAKER_STATE_INTERVAL_SECONDS=15`, `MOONRAKER_PRINT_INTERVAL_SECONDS=5`, `MOONRAKER_INFO_INTERVAL_SECONDS=300`, and `SYNC_OUTBOX_LOCK_TIMEOUT_SECONDS=300` unless measured deployment constraints require a documented override.
- Cap a failed periodic job's retry delay at that job's configured scheduling interval. In particular, active-spool reconciliation must retry within the 15-second default rather than inheriting the general one-hour exponential-backoff ceiling.
- After migration and initial seeding, include `integrations/klipper/filament-manager-macros.cfg` last, after the printer's existing start/end, load/unload, M600, purge, pause/resume, and cancel macros. Verify `[respond]`, `[save_variables]`, `[pause_resume]`, and `[virtual_sdcard]`, then let the worker initialize physical spool state once from the currently correct active Spoolman ID.
- Disable Fluidd's independent **Show spool selection dialog on print start** option. Replace only Cura's existing `START_PRINT` invocation with the documented `FILAMENT_MANAGER_START_PRINT ... MATERIAL_GUID={material_guid}` call; never let the workstation agent patch this setting. Use parameterless `LOAD_FILAMENT` or `FILAMENT_MANAGER_LOAD_TARGET` for the managed live chooser; a direct Spoolman selection is only a guarded target and is restored to the physical ID until confirmed.
- Test both spool paths before production: a matching managed product material reaches the existing `START_PRINT` unchanged, while a mismatch prompts for an exact spool, clears Spoolman after unload, and activates the new ID only after load. Confirm `FILAMENT_MANAGER_ABORT` preserves the last completed boundary. Test warning inspection first, then optional blocking with one match, one mismatch, and one unavailable file. Verify in-app physical unload, plate/mesh clear, `SELECT_BUILD_PLATE`, exact Print History state, and notification recurrence; save Side A as exact `P<number>` and Side B as exact `P<number>b`.
- Install the agent per user on Arch Linux with the hardened systemd user unit or on Windows 11 with the limited per-user logon task.
- The Arch user unit must permit both supported Cura data roots and their matching configuration roots so exact-version recovery can merge `cura.cfg`; retain read-only home protection everywhere else. After installing or resetting Cura, sign in and let Cura install account-owned plugins, close Cura, then queue the reviewed same-version recovery from Cura Workstations. Re-enter excluded connection credentials afterward.
- Workstation-agent HTTP clients must use an explicit verified operating-system TLS context, including for pairing, heartbeat, claim, and completion requests. This permits operator-installed private roots while retaining hostname/chain checks; never solve a private-CA failure with `verify=False`.
- Re-run the matching per-user installer to upgrade an agent. It must identify fresh installation versus upgrade, preserve private pairing/configuration and Cura backup/state directories, stage standalone replacements before stopping the old process, refresh the managed unit/task, and restart only when it was already running. On Arch, create the platformdirs title-case state/config roots before service start and list them as required `ReadWritePaths`; systemd cannot create a missing path beneath `ProtectHome=read-only`. Use the matching uninstaller to remove the per-user service/task and agent-owned executable, credential, state, and backup roots; it must leave deployed Cura material/plugin files untouched.
- Install/enable Cura Material Settings and Klipper Settings on each workstation. Verify agent contact, existing-material discovery/import before takeover, machine/nozzle matching, explicit authoritative enablement when user materials exist, closed-Cura deferral, full desired-state material replacement, automatic Template favorites, per-material two-line filler/finish descriptions with `None` fallbacks, complete Material Settings `visible_settings` alignment, central material-value enforcement, user quality-profile material-key cleanup, corrupt-profile quarantine, visibility-plugin installation, manifest checksums, drift repair, and rollback. The generated plugin must not call Cura's lazy `getMachineManager()` or schedule enforcement during registration; defer plugin preference alignment and both machine behaviors until `initializationFinished` so plugin loading cannot race active-machine restoration. Increment and test the deployment renderer revision whenever generated plugin or material-file behavior changes; this must invalidate the prior agent manifest without requiring a canonical profile edit.
- Validate Spoolman contract-sensitive changes against the pinned 0.23.1 image. Every managed extra field is declared as text, so a structured value such as `display_palette` requires compact inner serialization before the outer JSON custom-field encoding.
