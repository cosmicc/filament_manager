# Filament Manager Agent Guide

## Mission

Build and maintain Filament Manager, a security-focused, self-hosted application for filament inventory, measurements, material profiles, calibration, build plates, and supported Klipper ecosystem integration.

The product name is **Filament Manager**. Do not introduce the former project name in code, documentation, configuration, deployment objects, or user-facing copy.

## Authority and boundaries

1. The `filament_manager` PostgreSQL database is canonical.
2. Standalone Spoolman is the printer-facing operational projection and usage service.
3. Google Sheets is a one-way, read-only publication target.
4. The supplied workbook is an initial-import fixture only.
5. Filament Manager integrates with Spoolman through its supported REST API and periodic reconciliation; direct database access is prohibited.
6. The default production deployment uses the root `docker-stack.yml` to run Spoolman and Filament Manager together while keeping their remote PostgreSQL databases, roles, credentials, migrations, and backups separate. The independent stack files under `docker/` remain available when operational isolation is required.
7. Cura files are changed only by the outbound-only per-user workstation agent under `workstation-agent/`; the server never reaches into a workstation or listens on an agent port. After explicit takeover of a workstation with existing user materials, Filament Manager owns the complete user material library, synchronizes and favorites the current templates under the exact `Template <material type>` name and `Template` brand plus every current product profile, groups products without a manufacturer under the exact `Unknown` brand, appends each meaningful filament filler once to its Cura product label so otherwise identical colors remain distinguishable, treats missing, blank, `None`, and `No filler` values as filler-free names, and writes each material's filler and finish to its Cura description as `Filament Filler: <value>` and `Filament Finish: <value>` on separate lines, using `None` for an empty value. Managed Cura IDs are stable per template or exact product/printer/nozzle-diameter scope and never use immutable revision IDs as the live container identity. Before removing a stale managed material, safely back up and rewrite only exact legacy managed container references in bounded regular Cura extruder-stack files; preserve unrelated stack values and reject malformed or linked files. It removes stale user material files after backup and installs its visibility/enforcement plugin so bundled Cura materials are hidden and the central material-setting values win over Cura's higher profile layers. Cura main/custom profiles remain workstation-owned and are never synchronized or created by Filament Manager. After backup, remove only centrally managed material keys from valid user `quality_changes`, repair recoverable duplicate-section syntax, and quarantine malformed bounded regular files; never follow symlinks, touch bundled quality profiles, or alter unrelated quality settings. While Cura is closed, every managed-library deployment must safely back up and atomically overwrite the matched machine's saved `machine_start_gcode` with the exact `FILAMENT_MANAGER_START_PRINT` boundary containing Cura's explicit position-zero material GUID and temperature placeholders, and `machine_end_gcode` with `END_PRINT`. Track that machine file separately from generated files so drift is detected without making it eligible for stale-file deletion, and restore it on a failed deployment or rollback. The managed plugin must register without constructing Cura's lazy machine manager, processing active-machine state, or scheduling enforcement; from Cura's `initializationFinished` signal, align the Material Settings plugin's enabled-setting preference with the central catalog before connecting those behaviors. Increment the workstation deployment renderer revision whenever agent-generated managed files or app-owned saved machine settings change so an agent upgrade invalidates the prior local manifest and automatically requests safe replacement even when canonical material settings did not change. The Cura Material Settings plugin exposes stored values, and the Cura Klipper Settings plugin owns pressure advance and smooth time.
   Re-running either supported workstation installer is an in-place upgrade: identify fresh installation versus upgrade in its output, preserve pairing credentials and Cura backup/state data, and replace only managed code and service/task definitions. The Windows installer adds the executable directory to the current user's PATH, interactively completes first pairing, starts every paired installation immediately, and retains its limited per-user logon task; an unpaired task must not be started. Arch upgrades restart only a service that was already running. The Arch installer must create both platformdirs title-case state/config roots before starting the hardened service because systemd cannot create a missing `ReadWritePaths` target beneath read-only home protection. The supported uninstallers remove the per-user service/task and all agent-owned executable, credential, state, and backup files without deleting the currently deployed Cura material/plugin library.
   Workstation HTTPS uses a verified TLS context backed by the operating-system trust store so operator-installed private roots work without insecure bypasses. Preserve hostname and chain verification, honor the standard `SSL_CERT_FILE`/`SSL_CERT_DIR` overrides, and never add a disable-verification option.
   Before authoritative takeover, an Administrator maps any subset of reported Cura materials or saved print profiles to existing active templates in an explicit map-then-review dialog, with one source and one template used at most once in the batch. Read saved print profiles without modifying Cura, merge their global and first-extruder layers, import only approved literal settings, and never evaluate Cura expressions. Keep a named source selectable even when it contains no tracked literal override or every tracked value is an omitted expression. Lock confirmation to the exact reviewed source-ID set, whose content hashes change with importable source content; periodic heartbeats and unrelated workstation metadata must not invalidate an unchanged review. A single confirmation applies every mapping atomically, records provenance, updates linked profiles through normal inheritance, enables authoritative management, and queues synchronization; unmapped sources are intentionally discarded after backup.
   After takeover, the managed plugin may record bounded approved value changes only for known deterministic managed material GUIDs. It removes managed keys from Cura's user-change and quality-change layers, resolves canonical material values through a runtime overlay, and records an edit before removing the transient user-layer value so saving a Cura quality profile contains only Cura-owned settings. The outbound agent overlays those pending values on the complete deployed material before reporting them, retains a receipt while Cura remains open, and removes only an unchanged receipt after the server accepts it while Cura is closed. Each semantic change saves directly and idempotently to the matching current template or profile, cascades template inheritance immediately, and queues synchronization. Product materials may report only profile-editable settings; template-only values may be captured only from `Template` materials. Never admit a new Cura-created material into canonical state.
8. Docker deployments are environment-only: every deployer-supplied application setting and credential comes from scoped stack variables, with no mounted application Docker config and no Docker secrets. The current variable contract supports exactly one Moonraker printer. Treat credential variables as a transitional risk, restrict manager and Portainer access, keep populated `.env` files untracked with mode `0600`, and never log or render these values.
9. The container image health check is web-specific: it probes loopback with the public hostname from `FILAMENT_MANAGER_BASE_URL` so trusted-host validation remains enforced. Every worker or one-shot service must disable this inherited HTTP health check.
10. Successful CI for a `main` push publishes the Filament Manager container for AMD64 and ARM64 with `latest` and immutable `sha-<commit>` tags. Treat `latest` as a testing convenience; production deployments pin an immutable SHA tag or digest. Image publication does not authorize a Git tag or GitHub Release.
11. Remote PostgreSQL connections use `filament_user` and `spoolman_user` with TLS explicitly disabled on the operator-managed isolated database network. Preserve SCRAM authentication, narrow firewall and `pg_hba.conf` rules, and separate database ownership; this non-SSL contract is unsafe on shared or untrusted networks.
12. The container entry point automatically upgrades the Filament Manager schema before starting web or worker commands. Concurrent tasks coordinate with one bounded PostgreSQL session advisory lock; a failed or timed-out migration must stop startup. Keep the opt-out only for controlled recovery.
13. Filament Manager owns spool locations after initial adoption. A legacy spool with no canonical location may import one existing bounded free-text Spoolman location; every local edit, including clearing the field, makes the canonical value authoritative and reconciliation repairs later remote drift.
14. `filament_colors` owns the case-insensitive mapping from a solid human color name to its shared display palette. A solid palette change updates every matching product mirror and queues their Spoolman projections. Rainbow is a color with one fixed six-sample spectrum. Multicolor products choose one, two, or three product-specific samples so unrelated multicolor filaments never share a palette. Request validation retains that three-sample multicolor limit, while API responses accept the complete Rainbow palette. Validate mutation response models before commit so a representation failure cannot persist an edit that makes a collection unreadable. A filament's color may change only before any retained spool use or print history exists.
15. Printer information synchronization reads only documented Moonraker/Klipper server, printer, `configfile.settings`, and `toolhead` fields. Keep connection values server-side, sanitize all external text and numbers, and preserve manual manufacturer, model, nozzle material, extruder type, and notes.
16. Canonical inventory changes queue Spoolman projection immediately. The one-minute safety sweep must first import printer-recorded usage, then converge every vendor, filament, and spool so an empty/rebuilt Spoolman database and missed/dead jobs repair automatically. Provision managed custom fields through the supported API, JSON-encode their values, preserve unknown fields, paginate complete collections, and never overwrite remote remaining weight during metadata-only convergence. Explicit canonical net-weight corrections use Spoolman's supported `remaining_weight` spool update, never its physical gross-scale measurement endpoint; coalesce older actionable corrections per spool. Because managed fields are declared as Spoolman text fields, structured display metadata must be serialized to a compact inner JSON string before the outer custom-field JSON encoding.
17. The persisted `FILAMENT_MANAGER_SPOOL_STATE` Klipper macro is the physical loaded-spool authority after one-time initialization. A completed physical unload must clear Moonraker/Spoolman before insertion, and a completed physical load must set the exact new Spoolman ID; a requested target is never active early. A direct non-null Spoolman selection made while idle or waiting for a manual target becomes a guarded Fluidd confirmation/load target, then the worker restores Spoolman to the last completed physical boundary until confirmation. Direct clears, invalid selections, and drift during other phases are repaired without changing canonical state.
18. Cura print preflight uses the managed material GUID and the strict published-profile printer-side catalog to bypass a change only when the physical spool matches. Otherwise Fluidd must prompt for one exact eligible print spool and confirmation of insertion. The workstation agent saves the exact preflight call in the matched Cura printer's start G-code and saves `END_PRINT` as its end G-code. Manual `LOAD_FILAMENT`, `FILAMENT_MANAGER_LOAD_TARGET`, M600 selection, and guarded direct Spoolman targets use a separate live catalog of projected non-empty spools with a safe temperature from the newest non-archived exact profile or linked in-scope template; manual loading must not require publication or a separately staged macro variable. Keep `integrations/klipper/filament-manager-macros.cfg` as the complete reference and include it after the printer's existing motion macros. Filament Manager owns public `M600`, `LOAD_FILAMENT`, and `UNLOAD_FILAMENT` without `rename_existing`; the printer must expose its physical routines under the exact reserved `_FILAMENT_MANAGER_HARDWARE_LOAD` and `_FILAMENT_MANAGER_HARDWARE_UNLOAD` names before the app file is included. Continue wrapping the existing public `CANCEL_PRINT`, and leave Fluidd's independent print-start spool selector disabled. Print preflight suspends only the virtual-SD stream with `M25`, retains one app-owned resume latch across inspection, spool selection, and a deferred printer build-plate chooser, and releases the Cura file with `M24` only when that latch is set, a file remains loaded, `print_stats.state` is `paused`, and the separate Klipper `pause_resume` state is not paused. Never use `virtual_sdcard.is_active` as the release condition because Klipper makes it false after `M25`. Retry an unmet release condition no more than once every half-second for thirty seconds, then stop the delayed loop and show explicit Retry and Cancel actions. Cancellation must recognize the retained file/paused print state, cancel the delayed release, clear the latch and attempt counter, and issue `SDCARD_RESET_FILE` before the original cancellation cleanup when direct `M25` left a loaded file that neither virtual-SD nor `pause_resume` considers active. Keep the macro version visible through `FILAMENT_MANAGER_SPOOL_STATE` so operators can verify the exact installed reference. A printer `START_PRINT` that defers to the app's `SELECT_BUILD_PLATE` must expose `waiting_for_mesh`, stored temperature variables, and `_START_PRINT_CONTINUE`; the selector completes that printer-owned start routine before scheduling the app-owned file release.
19. G-code inspection defaults to warning while retaining evidence. Administrators may enable blocking; then an unresolved exact profile, unavailable bounded inspection, or supported mismatch must pause in Fluidd before spool selection when Cura entered the documented `FILAMENT_MANAGER_START_PRINT` gate. Commit the inspection evidence before acknowledging that external gate, derive the acknowledgement fail-closed from the persisted result, and retry it on later current-print passes while Klipper still reports the inspection phase so a state-read race or transient acknowledgement failure cannot leave Fluidd waiting indefinitely. A block condition observed outside that gate remains retained evidence but cannot retroactively pause a print; identify that distinction in Print History. Keep regular and initial-layer build-plate temperature evidence distinct: Moonraker's first-layer metadata, the managed `BED_TEMP` boundary, and the first bed-heating command may validate only the initial-layer value, while regular-temperature comparison requires the managed start boundary's explicit resolved `REGULAR_BED_TEMP`; skip that one comparison when its exact evidence is absent and never treat Cura's saved `SETTING_3 material_bed_temperature` quality-layer value as resolved material evidence. Read files only through supported Moonraker metadata/download endpoints, hash the complete bounded stream, retain bounded samples, and never evaluate Cura content.
20. Canonical print history imports supported Moonraker history and captures new exact state only after preflight finishes. Preserve immutable printer/spool/product/profile/plate snapshots, each exact segment's purchase-cost-per-gram and currency basis, G-code hashes, explicitly unresolved legacy state, the bounded supported raw Moonraker history outcome, and append-only M600 material segments and outcome-assessment revisions. Keep five-second live exact-state capture during a print, but defer the complete Moonraker history listing until the printer leaves `printing` or `paused` so history polling does not compete with motion timing. Present history through server-side newest-first pagination with a 10-record default, exact 10/25/50/100 choices plus First, Previous, Next, and Last navigation, and a printer filter defaulted to all printers. Tint completed, cancelled, and failed entries with subtle semantic backgrounds while retaining explicit status text. Accept browser query-string page sizes and printer IDs through explicit validation, and never render a failed history request as a genuine empty canonical history. Fetch only bounded raster thumbnails declared by supported Moonraker G-code metadata, reject unsafe relative paths, decode and resize them under strict limits, strip metadata by re-encoding to WebP, store them with the print, and serve them only through authenticated application endpoints; thumbnail failure must not fail print capture. Derive current and historical actual filament costs only from the captured segment bases, expose incomplete and mixed-currency results explicitly, and never reprice history from mutable spool inventory. Isolate malformed bounded legacy rows so one record cannot block the pass checkpoint or valid history; log only its bounded index and error class. Associate only conservatively matched moonraker-timelapse MP4 paths and stream them through an authenticated range-capable application endpoint; never expose the private Moonraker origin or API key. On completed, failed, or cancelled terminal jobs, subtract only Moonraker-reported actual segment use from every exact spool once, with idempotent usage events and no predicted fallback; do not double-subtract use already imported from Spoolman. Never relink historical records to current mutable state.
21. Operator notifications are persistent, deduplicated canonical events with per-user read state. Reappearing resolved conditions become unread. The browser notification panel closes on an outside pointer action while preserving every interaction inside the panel. Keep unavailable Moonraker, dead job, low/empty spool, plate maintenance, and failed Cura synchronization checks server-side and never expose external response bodies. Deduplicate Cura failures by workstation and operation from only the newest operation state; named recovery-capture failures remain request history under Recovery points and must not masquerade as active material synchronization alerts.
22. Filament Manager supports exactly one active Administrator account. An empty database creates `admin` / `admin`, hashes the password immediately, and requires a password change before any other application route is accessible. Existing single-account credentials remain unchanged during upgrade. Browser sessions use a thirty-day absolute lifetime and a rolling seven-day idle window; renew the idle deadline for an actively used session at most once every five minutes without extending its absolute expiry. The Administrator may change the username, display name, and password under Settings; identity or password changes revoke all other sessions. Refuse startup when legacy data contains more than one account so an operator must resolve that incompatible state before upgrading. Never return or retain plaintext passwords.
23. The worker automatically aligns the configured printer's exact P-number build-plate side and physical active spool with Moonraker every 5 seconds and refreshes sanitized printer information every 5 minutes. Cap failed periodic-job retry delays at their normal poll intervals so a transient failure cannot make active-spool state stale for more than one minute while Moonraker is reachable. Preserve these automatic defaults, keep manual integration actions optional, and never log connection credentials or external response bodies.
24. Physical nozzles are canonical inventory records with diameter, construction material, lifecycle status, and append-only install/remove events. A printer may have at most one installed nozzle. Installing a different diameter queues each managed workstation while Cura is closed, matches one exact position-zero extruder, backs up the machine/extruder/definition-change files, writes `machine_nozzle_size` to that selected extruder's existing definition-change container, reasserts the app-owned saved machine start/end G-code, selects an existing exact extruder nozzle variant when one is unambiguous, and then requeues the current material library. Every workstation heartbeat must read the exact linked position-zero extruder's saved `machine_nozzle_size`; when it differs from the installed canonical nozzle, queue a coalesced closed-Cura correction even if no recent nozzle-change event occurred, with bounded periodic retries for continuous drift. Never manufacture a Cura variant or definition-change file. A successful same-version Cura recovery must queue this alignment again so restored machine data cannot supersede the app's current nozzle or print boundary. Exact completed-print attribution and total filament use follow the nozzle captured on the immutable print job; do not rewrite history when a nozzle is later moved or retired.
25. Diagnostics is the single web surface for connection, synchronization, worker, queue, bounded operational error, running/latest-version, and canonical-database backup status; do not restore a separate Integrations browser page. Show actionable queue summaries and one current sanitized cause per failing job type, but never show the individual Projection operations / Recent jobs list. Recent errors and the matching authenticated text download use a one-day default with exact one-day, seven-day, and thirty-day choices. Distinguish retained error history from current health in both the page and download, and show every persisted validation check counted by its immutable summary instead of hiding non-recovery categories. Distinguish never-attempted pending work from a pending retry and show the next retry time. A successful recurring run supersedes older terminal runs of the same type; retain superseded history without counting it as actionable debt, and retire older reconstructable metadata upserts only after a newer equivalent/full projection succeeds. Never treat deletes or explicit weight adjustments as reconstructable. Moonraker state failures must identify the bounded failing sub-operation without exposing upstream bodies. Optional spool-preflight catalog publication has its own durable per-printer status, logs warnings only on state transitions, and must not fail an otherwise successful physical spool/build-plate reconciliation or accumulate recurring dead jobs. Query only the fixed public GitHub releases endpoint, include non-draft testing releases, cache results, and never expose upstream response bodies. Recovery validation is read-only and results are persisted; projection rebuilds only queue reconstructable Spoolman, Google, and managed Cura work and never mutate canonical business records or perform a live database restore. Never render or export credentials, URLs, SQL, external response bodies, or tracebacks.
26. Cura recovery snapshots are immutable, sanitized, exact-version workstation records captured automatically or through a named Administrator request only while Cura is closed. Retain the fifteen newest automatic snapshots per workstation installation/version; named points do not consume that quota and remain until explicit deletion. Content-deduplicate automatic points, allow a requested named point to preserve identical content, and block an apparent reset or large deletion from automatically replacing the last known-good point. An explicit named request may preserve the current reset state as a separate point when a printer configuration still exists. In Recovery points, list saved Cura configurations before recent request history, then show each request's pending, capturing, succeeded, or sanitized failed state. Names/descriptions are mutable audited metadata, and individual deletion requires confirmation and must be refused while a restore is pending. Remember only the identity checksum of an operator-deleted automatic point so unchanged content does not immediately reappear; changed content and explicit named captures remain allowed. An Administrator may explicitly review and restore a retained point from any paired workstation into a target installation reporting the exact same Cura version; the target agent backs up every affected local file, merges safe preferences without changing current login/connection secrets, then queues canonical nozzle alignment and the managed material library. Store the complete bounded non-sensitive printer, extruder, definition-change, user/quality, visibility, and machine option documents—including opaque start/end G-code—plus safe offline-plugin settings, behavior-only Cura2Moonraker preferences, and plugin name/version inventory; accept Cura setting-visibility presets' valid key-only lines without relaxing parsing for other configuration files. A rejected, unavailable, or locally invalid recovery capture must be logged safely, reported only through the recovery health surface with bounded path-free guidance, and must not mark the connected workstation agent unhealthy or prevent restore, nozzle, or material deployment claims from running. Never upload or restore account sessions, credentials, endpoints, absolute paths, plugin executables, materials, logs, caches, or model files.
27. Bugsnag error and browser-performance reporting is optional and disabled by default. Configure its SDK API key only through scoped environment variables; the browser key is an expected public identifier, not an account credential. Never send the separate Upload API key or a personal authentication token to the application. Never report raw exception messages, URLs, query strings, request/response bodies or headers, user/session data, hostnames, external response bodies, credentials, or submitted values. Normalize browser routes, suppress high-frequency polling spans, disable trace propagation, report only terminal outbox failures, and throttle recurring worker errors. Diagnostics and local structured logs remain canonical. Upload hidden source maps only from authorized direct-push CI using the `BUGSNAG_UPLOAD_API_KEY` repository secret, and never ship map files in the runtime image.
28. The central Cura material-setting catalog is authoritative over its required subset of the Material Settings plugin selection. After Cura initialization, add all 54 non-metadata managed keys, remove cleanup-only retired keys, preserve unrelated operator-selected settings, and verify the required keys against the active Cura machine definitions. Cura 5.13 uses `speed_ironing`; keep the quality-profile-owned `ironing_enabled`, obsolete `ironing_speed`, and removed `limit_support_retractions` keys retired and cleanup-only. The managed plugin writes one atomic value-free receipt containing only the catalog checksum, expected/exposed counts, missing/retired keys, required-plugin readiness, and verification time. The outbound agent binds the receipt to the deployed manifest, reports bounded Material Settings/Klipper Settings versions, and exposes healthy, waiting, degraded, or invalid status through Cura Workstations and Diagnostics. Never import the visibility-list selection itself as canonical application configuration.
29. The worker automatically creates compressed ZIP snapshots of only the canonical `filament_manager` PostgreSQL database on the Administrator-configured interval, defaulting to every 24 hours and retaining the newest ten automatic archives. Defer automatic and manual dump creation while a canonical print is in progress. After an automatic failure, use a persisted exponential retry delay beginning at fifteen minutes and capped at six hours; never respawn `pg_dump` every worker minute. The runtime image includes PostgreSQL client 18 so supported older servers and version 18 can be dumped, and command failures expose only bounded classified guidance. Each archive contains exactly one PostgreSQL custom-format dump and one bounded versioned manifest with exact size and SHA-256 evidence. Keep archives in the private shared application data volume, write them atomically with restrictive permissions, and fully validate imported/downloaded/restored archives without extracting caller-controlled paths. Manual, imported, and automatic archives are downloadable; imported trusted archives remain separate from automatic retention. Spoolman retains separate credentials and backups. Diagnostics may stage an exact typed-confirmed restore, but never restore the live database in a web or worker process. The dedicated zero-replica restore service runs only after web and worker are stopped, creates a pre-restore safety archive, restores in one PostgreSQL transaction without ownership or ACL changes, applies forward migrations, records recovery, revokes every restored browser session, and keeps a failed request available for controlled recovery.

## Core implementation rules

- Spools, Filaments, Build Plates, and Nozzles each offer **List**, **Cards**, and **Detailed** catalog presentations from a labelled toolbar selector. Preserve each page's view independently in browser storage and use that page's established presentation as its first-use default: list for Spools, cards for Filaments and Nozzles, and detailed for Build Plates. List is a flat information-dense row layout, Cards is compact, and Detailed uses larger two-to-three-column cards. Every presentation must retain the same complete record actions through navigation or an accessible selected-item detail modal. Spools must span the full content width and must never restore a permanent right-side selection panel.
- Within each catalog presentation, keep repeated rows/cards uniformly sized and bound long text with ellipsis or line clamping so content length cannot resize one record. Filament and Nozzle list rows open directly without redundant Open or Details buttons.
- Templates also use independently remembered List, Cards, and Detailed presentations. Each template offers a portable versioned JSON download. Import requires an explicit choice between a newly selected printer/nozzle/material scope and a confirmed overwrite of one existing template; portable files never select targets by stored database IDs.
- Mouse-wheel scrolling over a focused numeric input must scroll the page or containing modal and must never change the input value. Preserve keyboard arrow-key editing and normal typed entry.
- Every physical nozzle belongs permanently to one printer, and its code is case-insensitively unique within that printer. Every material template references that exact physical nozzle as well as its printer and cached diameter; reject mismatched printer/nozzle/diameter input and permit only one active template per normalized material type and physical nozzle.
- UUID technical keys, human spool IDs that may be corrected only before retained history and are immutable afterward, integer record versions, UTC storage, and America/Detroit display.
- PostgreSQL `NUMERIC`, never binary floating point, for mass, density, dimensions, calibrated factors, and money.
- Immutable measurement, usage, audit, and calibration-result history.
- Optimistic concurrency for mutable resources and idempotency keys for external writes and device events.
- Every canonical mutation records an audit event and creates external projection jobs in the same transaction when required.
- Preserve unknown Spoolman `extra` fields.
- Quantize Spoolman remaining-weight readings to the canonical `NUMERIC(12,3)` gram precision before comparing, recording usage, or building idempotency keys.
- New-spool entry accepts purchased filament-only weight plus an optional full-spool scale reading and infers empty-spool tare as gross minus filament. Pair optional purchase cost/currency with that net weight and derive the physical spool's cost per gram; project the same net weight and total price to Spoolman. Managed Cura materials are product-scoped, so publish a normalized currency-safe weighted cost rate across current usable priced spools and omit it when their currencies differ. Setup-only mistakes may be deleted, including their initial creation measurement; later measurements, corrections, use, prints, calibrations, or NFC bindings force archival. Current-mass corrections append a usage event and project the exact corrected weight.
- Treat spool locations as bounded free text. Import a Spoolman location only for a legacy canonical row that has never established location ownership; thereafter project the Filament Manager value back through the supported REST API.
- Google or Spoolman outages must queue work and must not corrupt canonical state.
- Workers coordinate immediate outbox delivery, one-minute complete Spoolman convergence, and Google publication with PostgreSQL advisory locks. Reclaim abandoned running jobs after the configured lock timeout. Keep `outbox_jobs.aggregate_version` as PostgreSQL `BIGINT`; manual system actions use microsecond timestamp identities that exceed a 32-bit integer.
- NFC UIDs are identifiers, not credentials. Scale readings remain telemetry until stability and identity checks pass.
- Workstation pairing codes are single-use and short-lived; agent bearer credentials are hashed, revocable, scoped only to agent endpoints, and never logged.
- Material templates are printer/nozzle scoped. New templates prefer the printer's installed nozzle. Template rows and cards open editing directly; portable JSON export and exact-name confirmed deletion live inside that editor rather than beside the catalog's primary controls. An existing template may move to another exact physical nozzle; move every linked current filament profile atomically to the new printer/nozzle-diameter scope, supersede all older published snapshots in the abandoned scope, and reject a target collision. Confirm template deletion by exact name, remove it from active choices and the managed template library, and retain its immutable revisions, linked profile snapshots, and audit history. User-facing edits save directly, while the database appends hidden immutable current-state snapshots for audit, exact print history, synchronization, and recovery. A filament may have multiple current profiles, with at most one current state per exact filament/printer/nozzle scope. Every profile links to its own current template snapshot, stores only sparse explicit differences, and retains a complete resolved snapshot; the product's source-template pointer is creation metadata and must never decide later inheritance. Determine the newest profile in every exact scope before filtering by inherited template identity so historical rebased-away profiles cannot become current again. Saving a template immediately creates current snapshots only for exact scopes whose current profile inherits that template, then invalidates every affected template/profile/filament client query; preserve each profile's explicit override keys even when an override temporarily equals the new template value, except for settings declared template-only. Prominently highlight each customized filament value and provide an exact **Revert to Template** action that erases its sparse override when saved. Density changes append one new snapshot for every current exact scope, and duplication copies the selected exact source scope rather than a global profile version. ## Documentation and release discipline

Keep `README.md`, `CHANGELOG.md`, `USER_CHANGELOG.md`, `VERSION`, this file, and affected skill files synchronized with meaningful changes. Changelog versions use `MM.DD.YYYY` dates and always contain Added, Changed, and Fixed sections.

At the start of repository work and again before release preparation, inspect every open automated dependency pull request. Merge a dependency update only when its compatibility ranges, full CI, lockfile, and relevant local tests show it is safe. Never bypass peer dependency resolution with force or legacy flags. Defer or close a blocked update with a concise reason, or combine linked major upgrades on a reviewed compatibility branch and merge them only after the complete set passes. Keep these dependency-only merges separate from unpublished application work.

Do not commit, push, tag, publish images, or create a release unless the user explicitly authorizes that boundary.
